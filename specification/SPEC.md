## Resolved this pass

- **`"Chunk already loaded?"` RuntimeException crashing the server during chunk generation/loading**, recurring on the live server (crash reports `crash-2026-10-03_22.13.51-server.txt` and others, all `java.lang.RuntimeException: Chunk already loaded?` at `codechicken.multipart.util.WorldTickScheduler$ChunkScheduler.onChunkLoad`). Already reported upstream by the user: [TheCBProject/CBMultipart#197](https://github.com/TheCBProject/CBMultipart/issues/197) - confirmed still open, no fix, no maintainer response.
  - **Root cause, verified against the real CBMultipart 3.5.0.155 bytecode** (`javap -c`, not guessed - decompiled `WorldTickScheduler.class` and `WorldTickScheduler$ChunkScheduler.class` directly from the jar deployed on the server):
    - `WorldTickScheduler.onChunkUnload(LevelChunk)` does `ticking.removeIf(scheduler -> scheduler.pos.equals(pos) && (scheduler.onChunkUnload(), true))` - i.e. it only calls the inner `ChunkScheduler.onChunkUnload()` (which just does `this.chunk = null`) for a scheduler still present in the `ticking` list at the moment of unload.
    - A `ChunkScheduler` that already finished its tick cycle for the current server tick (see `tick()`'s own `ticking = false` at the end) has already left `ticking` by then - so if that chunk happens to unload afterward, `onChunkUnload` finds nothing to null, and the scheduler's `chunk` field survives.
    - The scheduler itself is never removed from `WorldTickScheduler.chunks` (the `Map<ChunkPos, ChunkScheduler>` that backs `getChunkScheduler`/`onChunkLoad`) - it's a permanent per-chunk cache for the life of the level.
    - `WorldTickScheduler.onChunkLoad(LevelChunk)` looks the scheduler up in that same `chunks` map and calls `scheduler.onChunkLoad(newChunk)` on whatever it finds - which is the same stale `ChunkScheduler` instance from before. Its inner `onChunkLoad` does `if (this.chunk != null) throw new RuntimeException("Chunk already loaded?")` - and the stale reference is still non-null, so it throws, even though the referenced `LevelChunk` itself isn't actually loaded anymore.
  - **Fix**: new standalone server-only mod (`cbmultipart_chunkfix`, this project) with a single `@Inject(at = @At("HEAD"))` on `ChunkScheduler.onChunkLoad` that checks `this.chunk != null && !this.chunk.loaded` - i.e. a reference that's demonstrably stale (the old `LevelChunk`'s own `loaded` field already went false) - and clears it to `null` before CBMultipart's own check runs. A **genuine** double-load (the old reference's chunk is still actually `loaded == true`) is left completely alone and still throws exactly as before - this only neutralizes the proven-stale case, not CBMultipart's real safety check.
  - Verified `LevelChunk.loaded` is a public field without needing to guess: CBMultipart's own bytecode (`ChunkScheduler.tick()`) does a plain `getfield` on it from a different package (`codechicken.multipart` reading `net.minecraft.world.level.chunk.LevelChunk.loaded`) - the JVM verifier would reject that at class-load time if the field weren't public, so no access-widener/reflection is needed on our end either.
  - `targets = "codechicken.multipart.util.WorldTickScheduler$ChunkScheduler"` (string form, not a class literal) because the inner class itself is package-private in CBMultipart - a `.class` literal reference from our own package wouldn't compile.
  - Scoped `side="SERVER"` in `neoforge.mods.toml` - the bug is pure server-side chunk-load bookkeeping, nothing client-visible depends on it.
